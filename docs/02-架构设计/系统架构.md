# 系统架构设计

## 1. 文档目的

本文档用于说明当前系统的整体架构、模块职责、依赖关系和实现边界，作为后续补写 `service`、`action`、`storage`、`config` 等模块代码时的设计依据。

当前系统已经明确拆分为前端展示层、API 服务层、业务编排层、存储访问层、脚本执行层和配置管理层。后续开发应遵循本文档中的模块边界，避免重新回到前后端混杂、业务逻辑与存储逻辑混杂的旧实现方式。

---

## 2. 总体架构

```text
Browser / Client
      |
      v
Vue Web 前端
      |
      | HTTP / JSON API
      v
C++ Drogon Service
      |
      | 调用业务 Action
      v
Action / Use Case
      |
      +----------------+
      |                |
      v                v
Storage            Runtime Scripts
SQLite + Files     Convert Worker

Admin
  -> 手工执行 python 脚本
  -> 直接修改 SQLite + data/

Config
  -> Web
  -> Service
  -> Action
  -> Storage
  -> Scripts
```

系统采用分层架构：

1. `web` 是纯前端 Vue 模块，负责页面展示和接口调用。
2. `service` 是 C++ Drogon API 服务，负责路由、请求校验和响应封装。
3. `action` 是业务编排层，每个 API 原则上对应一个 action，用于组织实际业务流程。
4. `storage` 是基础设施层，负责面向 `service/action` 的 SQLite 元数据和文件资源读写。
5. `scripts` 是脚本执行层，用于异步转换，以及管理员手工执行的发布、回滚、下线和清理等操作。
6. `config` 是统一配置层，负责提供数据库路径、数据目录、脚本路径、端口和运行参数。

---

## 3. 模块职责

### 3.1 web

`web` 模块是纯前端 Vue 代码，不包含后端 C++ 逻辑。

主要职责：

1. 页面展示。
2. 页面运行时逻辑。
3. 页面区块渲染。
4. 调用 `service` 暴露的 HTTP / JSON API。
5. 在开发、预览或演示场景下使用内置 demo data。

边界约束：

1. 不直接访问 SQLite。
2. 不直接访问服务器文件系统。
3. 不直接调用 `scripts` 脚本。
4. 不实现真实业务规则。
5. 不处理正式环境下的发布、回滚、下线、清理等管理员维护动作。

说明：

`web` 中的 demo data 默认用于本地开发、页面预览或离线演示。正式环境中，页面数据仍应优先以 `service` API 返回结果为准；但当接口请求失败时，允许降级回退到本地 mock，同时页面必须明确标注当前数据来源。

---

### 3.2 service

`service` 模块是 C++ Drogon 服务层，负责对外提供 API。

主要职责：

1. 注册 Drogon 路由。
2. 接收 HTTP 请求。
3. 解析请求参数。
4. 执行基础参数校验。
5. 处理请求追踪、超时和基础运行保护。
6. 将 HTTP 请求转换为 action 输入对象。
7. 调用对应的 `action`。
8. 将 action 执行结果转换为统一 API 响应。
9. 处理错误码、HTTP 状态码和响应格式。

边界约束：

1. 不直接编排复杂业务流程。
2. 不直接访问 SQLite。
3. 不直接操作 `data/` 目录中的业务文件。
4. 不直接执行发布、回滚、下线和清理脚本。
5. 不把 Drogon 的 `HttpRequest`、`HttpResponse` 对象传入 `action` 层。

建议接口形态：

```text
HTTP Request
    -> service 解析为 Request DTO
    -> service 转换为 Action Input
    -> action 执行业务流程
    -> action 返回 Action Result
    -> service 转换为 HTTP Response
```

说明：

控制器属于 `service` 模块的内部实现，不单独作为一级模块。

---

### 3.3 action

`action` 模块是业务编排层，负责执行具体业务用例。

原则上，每个 API 或每个稳定业务用例对应一个 action，例如：

```text
GET  /api/v1/products                                   -> ProductsAction : 负责查询所有产品
GET  /api/v1/products/{product_code}/releases           -> ReleasesAction ：负责查询指定产品所有版本
GET  /api/v1/products/{product_code}/Document           -> DocumentAction ：负责查询指定产品版本详情
POST /api/v1/products/{product_code}/update-check       -> CheckUpdateAction ：负责检查更新
GET  /api/v1/products/{product_code}/releases/{version}/download
                                                       -> DownloadAction ：负责下载指定产品指定版本的全量包
POST /api/v1/products/{product_code}/convert-tasks      -> ConvertTaskAction.createTask() ：负责创建异步转换任务
GET  /api/v1/convert-tasks/{task_id}                    -> ConvertTaskAction.getTaskResult() ：负责查询异步转换任务结果

主要职责：

1. 检查更新。
2. 查询产品、版本和版本详情。
3. 选择下载包和版本详情资源。
4. 创建异步转换任务。
5. 推进转换任务状态机。
6. 进行业务规则校验。
7. 组织 `storage` 与运行时转换脚本完成在线业务流程。
8. 记录关键任务事件。

边界约束：

1. 不感知 Drogon 框架。
2. 不接收 Drogon `HttpRequest`。
3. 不返回 Drogon `HttpResponse`。
4. 不直接拼接 HTTP 响应格式。
5. 不直接读取配置文件，应使用注入后的配置对象。

`action` 是后端变化最频繁的业务编排层。为了便于测试和复用，`action` 应尽量与 HTTP 协议解耦。

补充设计要求：

1. 不建议把多个不相干 API 长期堆到一个 `ProductAction` 或 `ConvertAction` 超大类中。
2. 查询类 action 与命令类 action 应尽量分开，便于测试和状态控制。
3. `latest` 只是 `Document` 查询中的版本语义，不应单独制造第二套完全重复的业务实现。
4. `action` 应围绕稳定用例依赖 `storage` 能力，而不是要求 `storage` 为某个 API 直接返回拼好的 JSON 片段。
5. 转换任务场景使用单一 `ConvertTaskAction` 类即可，但应在类内明确区分 `createTask()` 与 `getTaskResult()` 两个稳定用例方法。

---

### 3.4 storage

`storage` 模块是基础设施层，负责元数据和文件资源的可靠读写。

主要职责：

1. 访问 SQLite 元数据。
2. 管理产品、版本、任务、审计等数据表。
3. 管理 `data/` 目录下的文件。
4. 读写版本详情页资源。
5. 读写上传件、转换结果、归档件和发布产物。
6. 提供事务能力。
7. 提供原子写入和原子替换能力。
8. 按 action 要求执行状态持久化。

边界约束：

1. 不知道页面如何渲染。
2. 不知道 HTTP API 协议细节。
3. 不决定业务状态是否允许流转。
4. 不直接执行 scripts。
5. 不向 web 暴露服务器真实文件路径。

推荐边界：

```text
action 决定状态流转是否合法
storage 负责把状态变化可靠写入数据库和文件系统
```

推荐实现形态：

```text
storage
  -> ProductRepository
  -> ReleaseRepository
  -> PackageRepository
  -> ReleasePageRepository
  -> ConvertTaskRepository
  -> AuditRepository
  -> FileStore
```

补充说明：

1. `storage` 不应按“某 API 要哪些字段”设计一批零散查询。
2. `storage` 应围绕产品、逻辑版本、包体、页面资源、转换任务等对象提供稳定接口。
3. `storage` 返回领域数据或存储对象，不返回 HTTP 响应结构。

---

### 3.5 scripts

`scripts` 模块是脚本执行层，不承接 Web 请求。

主要职责：

1. 旧数据转换。
2. 版本发布。
3. 版本详情页资源发布。
4. 版本回滚。
5. 版本下线。
6. 历史数据清理。
7. 其他离线或半离线维护任务。

边界约束：

1. 不反向依赖 `web`。
2. 不反向依赖 `service`。
3. 不直接接收 HTTP 请求。
4. 在线转换链路中的脚本应由 `action` 受控调用。
5. 管理员离线维护脚本由管理员在服务器本机人工执行。
6. 管理脚本允许直接修改 SQLite 和 `data/`，但必须遵守固定目录和状态约定。

建议区分两类脚本调用方式：

1. 面向客户端的在线转换脚本，由 `action` 通过统一脚本执行器异步调用。
2. 面向管理员的发布、回滚、下线和清理脚本，由管理员在服务器本机人工执行 `python/` 下固定脚本。

在线脚本执行器应统一处理：

1. 脚本路径白名单。
2. 参数转义。
3. 超时控制。
4. 退出码检查。
5. stdout / stderr 捕获。
6. 执行日志归档。
7. 错误结果转换。
8. 幂等性和重试策略。

---

### 3.6 config

`config` 模块负责统一管理运行配置。

主要职责：

1. 数据库路径。
2. 数据目录。
3. 脚本目录。
4. 服务端口。
5. 站点运行参数。
6. 上传大小限制。
7. 下载访问策略。
8. 任务执行超时。
9. 日志配置。

边界约束：

1. 各模块不应自行读取配置文件。
2. 配置应在程序启动时集中加载。
3. 配置对象应通过构造函数或初始化流程注入到各模块。
4. 避免形成隐式依赖。

## 4. 调用关系

### 4.1 正常 API 调用流程

```text
web
  -> service
      -> action
          -> storage
          -> scripts
```

说明：

1. `web` 只调用 `service` API。
2. `service` 只负责 API 层处理。
3. `service` 调用 `action` 完成业务用例。
4. `action` 根据需要调用 `storage` 和 `scripts`。
5. `storage` 负责数据和文件持久化。
6. `scripts` 在在线链路中主要承担后台转换脚本执行。

---

### 4.2 查询类接口流程

适用于产品列表、版本列表、版本详情等接口。

```text
web
  -> service
      -> query action
          -> storage
```

示例：

```text
GET /api/v1/products
GET /api/v1/products/{product_code}/releases
GET /api/v1/products/{product_code}/Document?version=latest
GET /api/v1/products/{product_code}/Document?version=2.3.1
```

说明：

查询类 action 通常不需要调用 scripts，只需要从 storage 读取数据并返回业务结果。

---

### 4.3 命令类接口流程

适用于需要创建后台任务的在线接口。

```text
web
  -> service
      -> command action
          -> storage 写入 Pending
          -> 后台 scripts 异步执行
          -> storage 更新最终状态
```

示例：

```text
POST /api/v1/products/{product_code}/convert-tasks
```

说明：

命令类 action 需要负责创建任务、启动后台执行、状态落库和失败处理，但不在 HTTP 请求中同步等待脚本完成。

---

### 4.4 版本更新与下载流程

适用于 `update-check` 与下载解析。

```text
客户端提交 product_code / client_version / platform / arch / channel
  -> service 校验参数
      -> CheckUpdateAction
          -> ReleaseRepository 解析 product + channel 的最新逻辑版本
          -> PackageRepository 定位目标平台包体
          -> action 比较版本并生成下载语义结果
              -> service 返回 need_update / latest_version / download
```

下载解析流程：

```text
客户端请求下载接口
  -> service 校验参数
      -> DownloadAction
          -> ReleaseRepository 校验版本存在
          -> PackageRepository 定位唯一包体
              -> service 返回 302 或文件流
```

---

## 5. 转换任务模型

转换任务强制采用异步模型，不允许在 HTTP 请求中同步执行完整转换流程。

推荐流程：

```text
web 创建转换任务
  -> service 接收请求
      -> action 创建任务记录
          -> storage 写入 Pending 状态
          -> 后台 scripts 或 worker 执行转换
          -> storage 更新任务状态

web 轮询任务状态
  -> service 查询任务
      -> action 查询任务状态
          -> storage 返回任务结果
```

推荐任务状态：

```text
Pending   待执行
Running   执行中
Success   执行成功
Failed    执行失败
Canceled  已取消
```

推荐接口：

```text
POST /api/v1/products/{product_code}/convert-tasks
GET  /api/v1/convert-tasks/{taskId}
```

说明：

1. 任务一旦开始执行，不提供公共取消接口。
2. `Canceled` 状态仅用于管理员人工介入或系统内部终止。
3. 初期如果暂不引入独立 worker，也应在服务进程内以后台方式执行，避免后续补充异步执行时大规模改造接口。

---

## 6. 核心领域对象关系

推荐后端核心对象关系如下：

```text
Product
  -> Release
      -> ReleasePackage

Product + Version
  -> ReleasePage

Product
  -> ConvertTask
```

补充说明：

1. `Release` 是逻辑版本，不直接等价于某一个安装包文件。
2. 同一 `Release` 下可以存在多个 `ReleasePackage`，分别对应不同平台和架构。
3. “当前最新版本”是 `Product + Channel -> Release` 的指针关系，不应由包体行上的 `is_latest` 表达。
4. 同一 `product_code + version` 的页面内容跨渠道共享，因此 `ReleasePage` 不再按渠道拆分；`channel` 只影响 `Document` 查询时的 latest 解析、状态判定和下载包选择。

---

## 7. 架构约束

1. 禁止 `web` 跨过 `service` 直接读取 SQLite、文件系统或脚本结果。
2. 禁止 `service` 直接编排复杂业务流程。
3. 禁止 `service` 直接访问 SQLite 或操作业务文件。
4. 禁止 `service` 直接执行 scripts。
5. 禁止 `scripts` 反向依赖 `web` 或 `service`。
6. 禁止 `storage` 感知页面渲染逻辑和 HTTP 协议细节。
7. 禁止各层自行读取配置文件形成隐式依赖。
8. 面向客户端的在线流程必须通过 `service -> action -> storage` 或 `service -> action -> scripts` 完成。
9. 发布、回滚、下线和清理不提供 HTTP API，只能由管理员人工执行 `python/` 脚本。
10. 管理脚本允许直接修改 SQLite 和 `data/`，但必须遵守统一的数据目录和状态约定。
11. 禁止把产品、逻辑版本、包体、页面资源、脚本路径混在一张版本表中。
12. 禁止把 `project_path`、源码路径、Vue 源码路径作为正式运行时业务元数据。

## 8. 安全边界

### 8.1 API 安全

`service` 应负责：

1. 请求参数校验。
2. 请求体大小限制。
3. 统一错误响应。
4. 请求追踪和日志关联。

`action` 应负责：

1. 业务规则校验。
2. 状态机校验。
3. 幂等性校验。
4. 失败补偿。

说明：

当前阶段不做鉴权、不做登录。

---

### 8.2 文件安全

`storage` 应负责：

1. 隐藏服务器真实文件路径。
2. 使用受控 key 或受控公共 URL 访问文件。
3. 防止路径穿越。
4. 控制上传文件类型和大小。
5. 使用临时文件 + 原子替换写入正式资源。

下载流程应为：

```text
web 请求下载资源
  -> service 校验请求
      -> action 判断资源是否可下载
          -> storage 返回受控文件流、受控路径或公共 URL
              -> service 输出下载响应
```

---

### 8.3 脚本安全

在线转换脚本只能通过 `action` 间接调用，并由统一的 `ScriptRunner` 执行。

管理员维护脚本虽然允许直接修改 SQLite 和 `data/`，但必须避免：

1. 直接拼接 shell 命令。
2. 使用未校验的用户输入作为脚本路径。
3. 让脚本自行访问未约定的业务目录。
4. 让脚本在没有状态记录的情况下修改正式数据。

---

## 9. 当前实现状态

当前仓库实现状态如下：

1. `web` 已经落地，是纯前端 Vue 代码，可独立构建与运行。
2. `service` 当前只保留占位结构，后续需要补充 Drogon 路由、请求解析、响应封装和错误处理。
3. `action` 当前只保留占位结构，后续需要按 API 补充对应 action。
4. `storage` 当前只保留占位结构，后续需要补充 SQLite 访问、文件存储和事务能力。
5. `config` 当前只保留占位结构，后续需要补充统一配置加载与注入机制。
6. `scripts` 作为脚本执行层存在；在线转换脚本后续由 action 通过 ScriptRunner 调用，发布、回滚、下线和清理继续保留为管理员手工执行的 `python/` 脚本。

后续编码应优先从以下顺序推进：

```text
config
  -> storage
  -> action
  -> service
  -> web API 对接
```

但从业务接口落地角度看，也可以先选择一条最小闭环，例如：

```text
产品列表 API
  -> service route
  -> ProductsAction
  -> ProductRepository
  -> SQLite 查询
  -> web 页面联调
```

## 10. 推荐目录结构

```text
project-root/
  include/
    action/
    config/
    service/
    storage/

  src/
    action/
    config/
    service/
    storage/

  web/                         # Vue 前端

  python/                      # 脚本执行层的物理目录
    convert/
    maintenance/
    publish/

  data/                        # 运行时数据目录，不建议提交到仓库
    database/
    uploads/
    converted/
    failed/
    packages/
    releases/
    logs/
```

说明：

1. 代码模块继续采用 `include/ + src/` 分层。
2. `scripts` 是逻辑模块名，当前物理目录为 `python/`。
3. 运行时目录统一使用 `data/`，不再使用 `storage/` 作为数据目录名称。

## 11. 设计结论

当前系统应采用清晰的分层架构：

```text
Vue web 只负责展示和 API 调用
Drogon service 只负责 HTTP API
Action 负责在线业务流程编排
Storage 负责 SQLite 和 data/ 持久化
Scripts 负责后台转换脚本和离线管理脚本
Config 负责统一配置注入
```

该架构的核心目标是：

1. 前后端彻底分离。
2. API 层与业务流程解耦。
3. 业务流程与存储细节解耦。
4. 在线脚本执行受控，离线管理脚本职责明确。
5. 配置集中管理，避免隐式依赖。
6. 后续可以逐步补齐 `service`、`action`、`storage` 和 `config`，而不需要恢复旧的混合实现。

后续实现时，应严格保持模块边界，优先建立一条从 `web -> service -> action -> storage` 的最小可运行链路，再逐步补充后台转换能力；发布、回滚、下线和清理继续按管理员手工脚本方案执行。
