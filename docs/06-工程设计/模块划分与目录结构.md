# 模块划分与目录结构

## 1. 一级模块

| 模块 | 职责 |
| --- | --- |
| `web` | Vue 页面、页面运行时、区块组件库、接口调用 |
| `service` | API 入口、控制器、请求校验、响应协议 |
| `action` | 业务编排、在线状态切换、异步任务流转与脚本调度 |
| `storage` | SQLite、文件目录、事务、原子切换 |
| `scripts` | 逻辑脚本模块；当前物理目录为 `python/`，包含转换脚本和离线管理脚本 |
| `config` | 全局配置 |

## 3. 关键说明

1. `include/` 下直接按模块和子目录组织，不保留旧的混合命名占位文件。
2. 版本详情查询统一围绕 `Document` 接口设计，不再保留 `latest` 专用控制器或 action。
3. `storage` 仅表示代码模块；根目录下的正式运行时数据目录统一命名为 `data/`。
4. `scripts` 是逻辑模块名，当前脚本物理目录为 `python/`，管理员在服务器本机人工执行其中的管理脚本。
5. 当前后端源码允许是空占位文件，但文件名和目录结构必须先与设计文档一致。

## 4. 推荐代码内部分层

### 4.1 `service`

建议包含：

1. `controllers/`
   Drogon 路由和控制器。
2. 后续如需扩展，可再补 `dto/`、`mappers/`、`responses/`。

当前最小集合：

1. `product_controller.*`
2. `document_controller.*`
3. `update_controller.*`
4. `convert_task_controller.*`
5. `ops_controller.*`

### 4.2 `action`

建议按稳定用例组织 action 文件，但命名保持简洁，不长期维持无边界的超大 `ProductAction` / `ConvertAction` 类。

推荐最小集合：

1. `products_action.*`
2. `releases_action.*`
3. `document_action.*`
4. `check_update_action.*`
5. `download_action.*`
6. `convert_task_action.*`

说明：

1. `latest` 只是 `Document` 查询中的一种版本语义，不再单独建 `/releases/latest` 专用 action。
2. 未显式传入 `channel` 时，action 应读取 `products.default_channel` 作为默认渠道。
3. `ConvertTaskAction` 作为单一 action 类，内部可拆分 `createTask()` 与 `getTaskResult()` 两个方法。
4. action 层输出建议使用稳定的结果对象，不直接暴露 Drogon 类型。

### 4.3 `storage`

建议继续拆分为仓储和文件能力：

1. `repositories/product_repository.*`
2. `repositories/release_repository.*`
3. `repositories/package_repository.*`
4. `repositories/release_page_repository.*`
5. `repositories/convert_task_repository.*`
6. `repositories/audit_repository.*`
7. `database/sqlite_connection.*`
8. `file_store.*`

说明：

1. 不建议让一个无边界的大类同时承担产品、版本、任务和页面查询。
2. `release_page_repository.*` 应按 `product_code + version` 读取共享页面资源。
3. 更不建议出现按 API 名字命名的存储函数，例如 `get_release_latest_api_data()`。

### 4.4 `config`

建议至少提供：

1. 数据库路径。
2. `data/` 根目录。
3. 公共 URL 前缀。
4. 上传大小限制。
5. 转换超时。
6. `convert_script_key -> real_path` 白名单映射。

## 5. 建议依赖方向

```text
service
  -> action interfaces / action results

action
  -> repository interfaces
  -> file store interfaces
  -> script runner interface

storage
  -> sqlite implementation
  -> filesystem implementation
```

## 6. 开发约束

1. 新增后端代码前，必须先判断属于 `service`、`action` 还是 `storage`。
2. `service` 不直接操作 SQLite 或文件系统。
3. `action` 不直接拼接前端渲染逻辑。
4. 发布、回滚、下线和清理不进入 `service` API，由管理员人工执行 `python/` 下固定脚本。
5. 高频变更内容优先落在 `data/` 与 `python/`，而不是频繁修改主程序结构。
6. `storage` 中保存的是对象级能力，不是某个 HTTP API 的专用 SQL。
7. 禁止把产品、逻辑版本、包体、页面资源、脚本路径混放进同一张“版本表”并在代码中长期扩展。
8. 禁止保留旧接口名对应的占位文件继续传播到新结构中。
