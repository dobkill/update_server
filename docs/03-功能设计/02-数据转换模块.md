# 数据转换模块

## 1. 目标

允许用户上传旧格式数据，由服务端创建异步转换任务，并在后台调用 `scripts` 脚本生成可下载结果。

## 2. 模块分工

| 模块 | 职责 |
| --- | --- |
| `web` | 提供上传界面、任务轮询页、结果下载入口 |
| `service` | 接收上传请求、任务查询请求和结果查询请求 |
| `action` | 创建任务、推进状态、按 `product_code` 调度对应脚本、记录失败原因 |
| `storage` | 保存上传文件、结果文件和任务状态 |
| `scripts` | 执行真实的数据转换 |

推荐 action 命名：

1. `ConvertTaskAction`

说明：

`ConvertTaskAction` 作为单一 action 类，内部承载 `createTask()` 与 `getTaskResult()` 两个稳定用例方法。

## 3. 业务流程

```text
用户调用 /api/v1/products/{product_code}/convert-tasks
并提交 form.product_code / source_version / target_version / file
-> service 解析请求
-> service 校验 Path 与 Form 中的 product_code 一致
-> action 创建任务
-> storage 写入任务初始状态 `Pending` 与上传件
-> action 以后台方式调度对应 scripts 转换脚本
-> storage 按执行进度回写 `Running / Success / Failed / Canceled`
-> 用户查询任务并获取结果下载地址
```

## 4. 核心模型拆分

转换模块至少应区分以下数据：

1. 产品级转换配置
   由 `product_code` 决定使用哪个脚本键，不直接把真实脚本路径暴露给接口层。
2. 转换任务
   保存任务 ID、产品编码、源版本、请求目标版本、实际解析目标版本、输入输出文件路径、日志、状态。
3. 转换文件
   上传件、结果件、失败件都只保存在 `data/` 目录，数据库只保存相对路径。

推荐规则：

1. `product_code` 必须写入 `convert_tasks`，不能只依赖请求阶段传参。
2. `target_version` 若传入 `latest`，应在 action 中按 `products.default_channel` 解析为实际版本后写入任务记录。
3. 真实脚本路径应由 `convert_script_key -> real_path` 白名单映射提供，而不是让调用方直接传路径。

## 5. 设计规则

1. 创建任务接口统一使用 `POST /api/v1/products/{product_code}/convert-tasks`。
2. 任务虽然属于某个产品，但查询接口使用全局 `task_id`。
3. 请求中必须显式传入 `product_code`，且 Path 与 Form 中的值必须一致，用于确定调用哪个产品的转换脚本。
4. 上传文件先写入 `data/uploads/convert/`。
5. 转换结果写入 `data/converted/`，失败件可转入 `data/failed/`。
6. 任务状态和错误信息由 `storage` 统一保存。
7. `action` 必须保证脚本异常时任务状态能正确落回 `failed`。
8. 查询任务接口在成功时直接返回 `result.download_url`，不再单独提供结果接口。
9. 当前阶段不做鉴权和登录。
10. 任务一旦开始执行，不提供取消接口；`Canceled` 状态仅用于管理员人工介入或系统内部终止。
11. `storage` 只负责可靠保存任务和文件路径，不负责决定任务状态是否合法流转。
12. 脚本执行必须通过统一 `ScriptRunner`，处理白名单、超时、退出码和日志归档。

## 6. 返回原则

1. 创建任务优先返回 `202 Accepted`。
2. 查询任务返回 `task_id / product_code / status / progress / error_message / result`。
3. 任务成功时在同一个查询接口中返回公共 `download_url`，未完成时 `result = null`。
4. 任务状态统一使用 `Pending / Running / Success / Failed / Canceled`。
5. 结果文件过期清理由管理员人工执行 `python/` 清理脚本。
