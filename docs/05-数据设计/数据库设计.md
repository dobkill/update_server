# 数据设计

## 1. 总原则

1. `storage` 是面向 `service/action` 的正式数据访问层，既包含 SQLite 访问，也包含文件目录访问。
2. SQLite 只保存元信息、状态、路径、时间和审计记录。
3. 包体、版本详情页资源、上传件、转换结果都保存在 `data/`。
4. 表结构设计以支撑在线任务状态切换，以及管理员脚本执行后的版本资源变更追踪为主。
5. 管理员人工执行的 `python/` 脚本可以直接修改 SQLite 和 `data/`，但仍应遵守本文档约定的目录结构和状态字段。
6. 数据表设计必须围绕稳定的业务对象建模，不应按某个 API 直接拼字段，也不应把产品、逻辑版本、包体、页面资源和脚本路径混放到一张表中。

## 2. 核心对象划分

为了避免旧设计中“一张大表承载所有含义”的问题，后端数据模型统一拆分为以下对象：

1. `Product`
   表示一个对外可见的软件产品，例如 `project-manage`。
2. `Release`
   表示某产品在某渠道下的一个逻辑版本，例如 `project-manage / 2.3.1 / stable`。
3. `ReleasePackage`
   表示某逻辑版本下某平台、某架构对应的具体安装包。
4. `ReleasePage`
   表示某产品某版本共享的版本详情页资源和页面数据，同一 `version` 在不同 `channel` 下共用同一套页面内容。
5. `ConvertTask`
   表示一次异步数据转换任务。
6. `AuditLog / PublishRecord`
   表示关键动作和发布轨迹。

其中最重要的拆分原则如下：

1. `Release` 是逻辑版本，不直接保存安装包二进制信息。
2. `ReleasePackage` 只描述某个平台包体，不承担“当前最新版本”语义。
3. “最新版本”不通过包体行上的 `is_latest` 实现，而通过独立的渠道头指针表维护。
4. 同一 `product_code + version` 的页面内容跨渠道共享，`channel` 只影响最新版本解析、状态判定和下载包选择。
5. `convert_script_path` 不作为版本数据字段保存，而由产品级配置键或统一白名单配置决定。
6. `project_path`、源码目录、Vue 源码路径都不是运行时正式元数据，不进入 SQLite 核心表。

## 3. SQLite 建议表

### 3.1 `products`

保存产品级信息。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `product_code` | `TEXT PRIMARY KEY` | 产品唯一编码 |
| `name` | `TEXT NOT NULL` | 产品名称 |
| `summary` | `TEXT` | 产品简介 |
| `cover_image_rel_path` | `TEXT` | 封面图相对路径 |
| `default_channel` | `TEXT NOT NULL` | 默认渠道，例如 `stable` |
| `convert_script_key` | `TEXT` | 转换脚本配置键，不直接保存物理路径 |
| `status` | `TEXT NOT NULL` | `active / disabled` |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

说明：

1. `convert_script_key` 由配置映射到白名单中的真实脚本路径。
2. `product_code` 是几乎所有业务表的稳定外键起点。

### 3.2 `releases`

保存逻辑版本信息。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY` | 主键 |
| `product_code` | `TEXT NOT NULL` | 所属产品 |
| `version` | `TEXT NOT NULL` | 版本号 |
| `channel` | `TEXT NOT NULL` | 发布渠道 |
| `title` | `TEXT NOT NULL` | 版本标题 |
| `release_notes_summary` | `TEXT` | 发布说明摘要 |
| `published_at` | `TEXT` | 发布时间 |
| `status` | `TEXT NOT NULL` | `draft / published / offline / archived` |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

约束建议：

1. `UNIQUE(product_code, version, channel)`。
2. `product_code` 外键引用 `products.product_code`。

说明：

1. `releases` 只描述“某产品在某渠道下的某个逻辑版本”。
2. 不在本表放 `platform`、`arch`、`file_path`、`sha256` 等包体字段。

### 3.3 `product_channel_heads`

保存“某产品某渠道当前指向哪个最新版本”。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `product_code` | `TEXT NOT NULL` | 产品编码 |
| `channel` | `TEXT NOT NULL` | 渠道 |
| `release_id` | `INTEGER NOT NULL` | 当前最新版本指向 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

约束建议：

1. `PRIMARY KEY(product_code, channel)`。
2. `release_id` 外键引用 `releases.id`。

说明：

1. 这是替代 `is_latest` 的核心设计。
2. 切换最新版本时，只更新这一行指针即可。
3. 该设计可以避免同一逻辑版本下多个平台包体反复写 `is_latest` 造成的不一致。

### 3.4 `release_packages`

保存可下载安装包元信息。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY` | 主键 |
| `release_id` | `INTEGER NOT NULL` | 所属逻辑版本 |
| `platform` | `TEXT NOT NULL` | 平台，例如 `windows` |
| `arch` | `TEXT NOT NULL` | 架构，例如 `x64` |
| `file_name` | `TEXT NOT NULL` | 文件名 |
| `file_rel_path` | `TEXT NOT NULL` | 相对路径 |
| `file_size` | `INTEGER NOT NULL` | 文件大小 |
| `sha256` | `TEXT NOT NULL` | 摘要 |
| `status` | `TEXT NOT NULL` | `active / deleted` |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

约束建议：

1. `UNIQUE(release_id, platform, arch)`。
2. `release_id` 外键引用 `releases.id`。

说明：

1. 下载包通过 `product_code + version + channel + platform + arch` 唯一定位。
2. 对外下载地址由服务层拼接公共 URL，不直接暴露 `file_rel_path`。

### 3.5 `release_pages`

保存版本详情页资源。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY` | 主键 |
| `product_code` | `TEXT NOT NULL` | 产品编码 |
| `version` | `TEXT NOT NULL` | 版本号 |
| `vue_entry_rel_path` | `TEXT NOT NULL` | 发布后的入口脚本相对路径 |
| `page_data_rel_path` | `TEXT NOT NULL` | 页面数据相对路径 |
| `assets_rel_dir` | `TEXT` | 页面附属资源目录 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

说明：

1. 不保存 Vue 源码目录路径。
2. 同一 `product_code + version` 的页面资源在不同渠道之间共享，不重复存储。
3. 是否可对外展示统一以 `releases.status` 判定，不再单独维护 `release_pages` 的发布状态字段。

### 3.6 `convert_tasks`

保存异步转换任务。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `task_id` | `TEXT PRIMARY KEY` | 全局任务 ID |
| `product_code` | `TEXT NOT NULL` | 产品编码 |
| `source_version` | `TEXT NOT NULL` | 原始版本 |
| `requested_target_version` | `TEXT NOT NULL` | 请求中的目标版本，可为 `latest` |
| `resolved_release_id` | `INTEGER` | 实际解析出的目标逻辑版本 |
| `input_file_rel_path` | `TEXT NOT NULL` | 上传件相对路径 |
| `output_file_rel_path` | `TEXT` | 输出结果相对路径 |
| `log_file_rel_path` | `TEXT` | 执行日志相对路径 |
| `status` | `TEXT NOT NULL` | `Pending / Running / Success / Failed / Canceled` |
| `progress` | `INTEGER NOT NULL DEFAULT 0` | 进度 `0-100` |
| `error_message` | `TEXT` | 失败原因 |
| `expire_at` | `TEXT` | 任务过期时间 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

说明：

1. `product_code` 必须入库，不能只存任务和版本号。
2. `requested_target_version` 与 `resolved_release_id` 分开保存，便于区分用户输入和实际解析结果。
3. 若用户传入 `latest`，action 在创建任务时按 `products.default_channel` 解析为具体 `release_id` 后入库。

### 3.7 `release_publish_records`

记录版本详情页或版本资源的发布、回滚、下线等动作。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY` | 主键 |
| `product_code` | `TEXT NOT NULL` | 产品编码 |
| `release_id` | `INTEGER` | 关联版本 |
| `action` | `TEXT NOT NULL` | `publish / rollback / offline / archive` |
| `operator` | `TEXT` | 操作人 |
| `detail` | `TEXT` | 详细说明 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |

### 3.8 `audit_logs`

记录系统关键动作和管理员操作。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY` | 主键 |
| `operator` | `TEXT` | 操作人 |
| `action` | `TEXT NOT NULL` | 动作名 |
| `target_type` | `TEXT` | 目标类型 |
| `target_id` | `TEXT` | 目标标识 |
| `detail` | `TEXT` | 补充说明 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |

## 4. 推荐索引与约束

建议至少补充以下索引：

1. `releases(product_code, channel, published_at DESC)` 用于版本列表和最新版本查询。
2. `release_packages(release_id, platform, arch)` 用于下载定位。
3. `convert_tasks(product_code, status, created_at DESC)` 用于任务维护和后台扫描。
4. `release_pages(product_code, version)` 用于版本详情页资源定位。

建议至少补充以下约束：

1. 同一 `product_code + channel` 只能有一个 `product_channel_heads` 指针。
2. 同一 `release_id + platform + arch` 只能存在一个有效包体。
3. 同一 `product_code + version` 只能存在一份共享版本详情页资源。
4. 所有状态字段必须使用固定枚举值，避免脚本和主程序写出不一致的字符串。
5. 发布脚本在切换最新版本时必须带事务，确保 `releases` 与 `product_channel_heads` 一致。

## 5. 文件存储目录

建议保持以下结构：

```text
data/
├── database/
├── uploads/
│   └── convert/
├── converted/
├── failed/
├── packages/
│   └── project-manage/
│       └── 2.3.1/
│           └── stable/
│               └── windows/
│                   └── x64/
├── releases/
│   ├── staging/
│   │   └── project-manage/
│   │       └── 2.3.1/
│   ├── active/
│   │   └── project-manage/
│   │       └── 2.3.1/
│   └── archive/
│       └── project-manage/
│           └── 2.3.1/
└── logs/
```

其中：

1. `packages/` 按 `product_code / version / channel / platform / arch` 分层，保存包体文件。
2. `releases/staging/` 用于页面资源暂存，`releases/active/` 用于正式生效资源，`releases/archive/` 用于归档。
3. `releases/active/{product_code}/{version}/entry.js` 和 `page-data.json` 表示当前版本详情页资源；由于同一 `version` 跨渠道共用页面内容，因此目录中不再编码 `channel`。
4. `releases/.../assets/` 保存图片和附件。
5. `uploads/convert/` 保存原始上传件，`converted/` 保存转换结果，`failed/` 保存失败件。
6. `logs/` 保存转换脚本和发布脚本的执行日志。
7. 对外访问必须走公共 URL，不直接暴露真实磁盘目录。
8. 包体公共访问地址建议编码完整定位信息，例如 `/public/packages/{product_code}/{version}/{channel}/{platform}/{arch}/{file_name}`。

## 6. Storage 模块边界建议

`storage` 模块应按对象能力提供接口，而不是按 API 直接写“查询 products 接口所需字段”这类方法。

推荐最小仓储边界：

1. `ProductRepository`
   负责产品查询和产品配置读取。
2. `ReleaseRepository`
   负责逻辑版本查询、最新版本解析和版本列表读取。
3. `PackageRepository`
   负责安装包查询和下载资源定位。
4. `ReleasePageRepository`
   负责按 `product_code + version` 读取共享版本详情页资源路径。
5. `ConvertTaskRepository`
   负责任务创建、状态流转和结果查询。
6. `AuditRepository`
   负责审计与发布记录。
7. `FileStore`
   负责相对路径到正式文件操作的封装。

边界规则：

1. `action` 决定业务状态是否允许流转。
2. `storage` 负责把合法的状态变化可靠落库。
3. `storage` 不感知 HTTP API 结构，也不直接拼接响应 JSON。

## 7. 设计约束

1. 所有状态切换必须带事务。
2. 所有文件发布必须先写 `staging`，再原子替换。
3. 同一时刻的“当前有效版本”必须能被唯一识别。
4. 任意脚本失败后，都必须能通过 SQLite 状态和日志追踪。
5. 转换任务状态统一使用 `Pending / Running / Success / Failed / Canceled`。
6. 所有路径字段统一保存相对路径，不保存面向外部的公共 URL。
7. 公共下载 URL 和页面访问 URL 由 `service` 或统一 URL 解析器生成。
8. 对外是否返回版本详情页，统一以 `releases.status` 判定；`release_pages` 只保存资源路径，不单独决定可见性。
9. 严禁把 `project_path`、源码目录路径、未发布的前端工程路径写入正式业务表。
